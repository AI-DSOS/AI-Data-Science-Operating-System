## When to Use
Before starting any module-sized unit of work (a DSOS phase, a bootcamp phase, a project milestone).

## Steps

1. Write done-criteria first, concretely — not "work on X," but the specific artifacts/scores that mean X is finished.
2. Estimate sessions needed based on similar past work, not optimism.
3. Check `docs/operating-system/time-blocking.md`'s current weekly map for conflicts with the bootcamp phase or Vaagai commitments.
4. If the estimate exceeds what fits before the next Weekly Review, split into two sprints now — don't let it run open-ended.
5. Copy `templates/sprint-definition-template.md`, fill it in.
6. Slot the sessions into the coming week(s) per `docs/operating-system/daily-operating-system.md`.

## Common Pitfalls

- Starting work with a vague goal ("make progress on X") instead of a checkable done-criteria.
- Not checking for conflicts before committing to the sprint, then discovering the time doesn't exist.

## Checklist

- [ ] Done-criteria concrete and checkable
- [ ] Session estimate based on past actuals
- [ ] Conflicts checked against current time-blocking
- [ ] Split into smaller sprints if too large for the coming week
